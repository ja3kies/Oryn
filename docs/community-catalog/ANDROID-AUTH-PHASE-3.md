# Phase 3 — audit et validation Auth, préparation du catalogue

Branche : `feature/community-epub-catalog`. Audit du code de phase 2 effectué avant modification, le 2 novembre 2026. Les changements non commités des phases précédentes sont préservés. Aucun compte, SQL, bucket, migration ou Edge Function Supabase n'a été créé ou déployé.

Ce contrôle est ciblé sur Auth Android ; il ne remplace pas l'audit complet avant publication prévu par `SECURITY-PLAN.md`. `getUser`/`/user` ne garantit pas la révocation immédiate d'un JWT déjà émis : l'accès doit aussi être contrôlé côté serveur, et la durée de vie du JWT reste une limite explicite. Aucune recommandation de source EPUB ni garantie de sécurité du contenu n'est introduite.

Références relues : changelog Supabase (notamment retrait des ciphers CBC), guides PKCE, sessions et redirections, validation des destinations dans le serveur Auth (`internal/utilities/request.go`). Les observations du code serveur courant ne prouvent pas le comportement d'une version de projet non encore fournie.

## Configuration Supabase isolée préparée

Le fichier [auth-isolated.properties.example](auth-isolated.properties.example) contient les propriétés complètes, vides et désactivées. L'application ne lit pas ce modèle. Aucun `local.properties` n'a été créé et aucune valeur fictive n'active le client.

Prérequis à fournir par l'opérateur : un projet Supabase Auth de test distinct, un fournisseur OAuth de test, un domaine HTTPS réellement contrôlé et un appareil Android de test. Aucun identifiant/accès de provisioning n'est configuré dans cet environnement ; aucun projet distant n'a donc été créé. La CLI Supabase n'est pas installée. Ne pas lier le répertoire `supabase/` existant à un projet pour cette validation.

Procédure de configuration, exclusivement dans ce nouveau projet isolé :

1. Vérifier et noter le propriétaire, la référence du projet et l'absence de données réelles, sans copier de secrets dans le rapport. Utiliser un compte utilisateur de test et une application OAuth de test séparés de la production. Ne pas appliquer les migrations catalogue, ne pas créer de bucket EPUB et ne pas déployer les fonctions existantes.
2. Activer seulement le fournisseur choisi dans Auth. Conserver son secret dans la configuration serveur Supabase isolée ; jamais dans Android, local.properties, Gradle ou Git. Le callback déclaré chez le fournisseur est l'origine gateway Supabase isolée suivie de `/auth/v1/callback`, distinct du callback Android. Refuser les comptes anonymes.
3. Préparer le domaine App Link. Servir `/.well-known/assetlinks.json` en HTTPS avec une chaîne TLS valide, sans redirection : relation `delegate_permission/common.handle_all_urls`, namespace `android_app`, package `com.example.oryn.reader` et empreinte SHA-256 réelle du certificat de signature du build de test. Obtenir cette empreinte via `./gradlew :app:signingReport`, sans lire/exporter la clé privée. Aucun domaine ni fingerprint fictif ne convient.
4. Dans les URL Auth Supabase isolées, fixer le callback à l'hôte réel et au seul chemin `/auth/callback`. Le `redirect_to` contient un nonce dynamique : une entrée exacte sans query peut ne pas l'accepter. Sur la version testée, utiliser un motif de query limité au suffixe `\?oryn_state=**` après l'origine et le chemin exacts. Le `?` est littéral/échappé selon la syntaxe glob Supabase ; le `**` est uniquement après le début de query (le nonce peut contenir des points). Aucun wildcard sur l'hôte ou le chemin. L'application exige toujours le nonce exact, refuse les paramètres supplémentaires et n'accepte aucune autre destination.
5. Vérifier ce motif sur le vrai serveur avant de déclarer l'environnement prêt : nonce conservé, absence de fallback silencieux sur Site URL, refus des hôtes/chemins/ports incorrects. Dans le code Auth consulté, l'origine Site URL peut autoriser toutes ses paths indépendamment de l'allowlist : choisir une origine de repli HTTPS contrôlée distincte de l'origine callback, sans redirection ouverte ni scripts/analytics qui copient des codes. Les règles effectives de la version isolée doivent être testées ; ne pas élargir le motif pour faire passer un échec.
6. Fusionner les valeurs publiques réelles du modèle dans `local.properties` ignoré par Git, sans écraser `sdk.dir` ni les propriétés existantes. L'origine Supabase est la gateway HTTPS sans chemin/query, et la clé uniquement `sb_publishable_…`. Renseigner le fournisseur et l'hôte de retour en minuscules. Garder `community.auth.enabled=false` pendant la vérification de l'isolation, de TLS et d'assetlinks ; passer les deux flags à true seulement pour le debug isolé après ces contrôles.
7. Sans ces prérequis : ne pas activer Auth. Un Supabase local peut remplacer le projet hébergé seulement avec une gateway HTTPS de test correctement certifiée et joignable par le navigateur/fournisseur. Aucun HTTP/cleartext, certificat ignoré, trust-all ou schéma custom de secours n'est autorisé.

Le motif de redirection doit être validé avec le nonce réel dans le navigateur sans le recopier dans un rapport ou un historique shell. Les wildcards de query ne désactivent ni PKCE, ni le nonce, ni la validation du chemin Android. Si la version Supabase ne conserve pas exactement la query attendue, conserver Auth désactivé et revoir la configuration.

## Scénario Android réel restant

État observé dans cet environnement : ADB démarré, `adb devices -l` ne liste aucun appareil ; aucun émulateur installé, aucun domaine de retour configuré et aucun projet Auth isolé accessible. Les scénarios ci-dessous sont **préparés, non exécutés**.

Utiliser un appareil/profil Android dédié aux tests, sans bibliothèque personnelle ; ne jamais faire `pm clear`, désinstaller Oryn, changer le schéma Room ou effacer ses données pour faciliter un test. Exécuter au minimum une fois sur API 24–30 puis sur API 31+ ; ajouter un reboot physique au test de fermeture du processus. Installer uniquement l'APK debug configuré pour le projet isolé. Les variables shell mentionnées ci-dessous désignent le vrai profil/appareil de test, jamais une valeur de secours.

### Prévol App Link et installation

- Construire `./gradlew :app:assembleDebug`, puis installer l'APK dans le profil de test sans effacer ses données. Vérifier package, certificat et hôte dans le manifeste fusionné.
- API 31+ : `adb shell pm verify-app-links --re-verify com.example.oryn.reader`, puis `adb shell pm get-app-links --user "$ORYN_TEST_USER_ID" com.example.oryn.reader`. Attendre le résultat de la vérification réseau, avec l'hôte contrôlé en statut `verified` et l'ouverture de liens autorisée pour ce profil. Ne jamais forcer `verified` avec `set-app-links` ni contourner le contrôle pour obtenir un succès.
- API 24–30 : contrôler assetlinks et le certificat indépendamment, la résolution HTTPS vers Oryn et les réglages système. Une sélection utilisateur « toujours ouvrir » ne prouve pas la vérification du domaine. Sans cette preuve externe, le test reste non validé et les flags d'activation restent false.
- Relever uniquement les états, versions OS/serveur, références non secrètes, chemins d'endpoint et codes HTTP. Ne pas capturer de corps de réponse, Authorization, refresh/access tokens, code verifier, nonce ou callback valide dans logcat, captures vidéo, captures réseau déchiffrées, presse-papier, captures d'écran ou rapport.

### Test de contrat Supabase réel optionnel

Conserver les valeurs hors Git et hors arguments CLI : `ORYN_AUTH_TEST_ISOLATED_VERIFIED=true`, `ORYN_AUTH_TEST_URL`, `ORYN_AUTH_TEST_PUBLISHABLE_KEY`, `ORYN_AUTH_TEST_REDIRECT_HOST`, `ORYN_AUTH_TEST_PROVIDER`, `ORYN_AUTH_TEST_ACCESS_TOKEN` d'un utilisateur dédié. Avec un lanceur qui ne journalise pas ces variables, exécuter `./gradlew --no-daemon :app:testDebugUnitTest --tests '*IsolatedAuthContractTest'`. Pas de `--debug`, de shell `set -x` ni de copie de token dans l'historique.

Sans opt-in, le test est ignoré avant même de lire les autres variables. Avec opt-in mais configuration incomplète/invalide, il échoue avant HTTP. Il n'effectue qu'un GET `/user` : aucune création de compte, rotation, révocation, requête catalogue ni SQL. Les parcours OAuth et Keystore/App Links restent à exécuter selon A1–A12 même si ce GET réussit.

## Conditions de préparation du catalogue

Le catalogue conserve `PRODUCTION_VERIFIED = false` indépendamment de l'état Auth ; les tests existants interdisent toute lecture de session ou requête catalogue sous ce verrou. Aucun endpoint communautaire d'upload, téléchargement ou partage n'est ajouté. Room, la bibliothèque locale et leurs préférences sont hors périmètre.

Avant une phase ultérieure : preuve de test Auth réel sur appareil, contrat de recherche publié, isolation RLS avec deux utilisateurs et anonyme, quotas/modération/retrait, audit de sécurité requis et autorisation distincte de déploiement. Une réussite des tests JVM n'autorise aucune activation publique ni partage automatique.
